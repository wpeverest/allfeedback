# Architectural Patterns

> Last updated: session 3 (form builder API completed and field types aligned).

## 1. Service Provider Pattern

Every subsystem implements `src/Core/ServiceProvider.php` (interface) with two lifecycle hooks:

- `register(ContainerBuilder)` — bind classes into the DI container before it compiles
- `boot()` — wire WordPress actions/filters after the container is ready

Providers: `AppServiceProvider`, `CoreServiceProvider`, `ApiServiceProvider`, `Admin\AdminServiceProvider`, `Frontend\FrontendServiceProvider`.

This keeps binding declaration separate from hook registration.

---

## 2. Dependency Injection (PHP-DI)

- Constructor parameters are auto-wired by type hint.
- Explicit bindings and factories live in `config/services.php`.
- In production the container compiles to a PHP cache file (see `src/Core/Container.php`).
- Access the container anywhere via `Plugin::getInstance()->getContainer()`.

Controllers receive repository + service dependencies through constructor injection; they never `new` collaborators.

---

## 3. Domain-Driven Design Layers

```
src/Domain/        Pure business rules — no WordPress, no HTTP
src/Application/   Use-case services — orchestrate domain objects
src/API/           REST controllers — parse input, call services, map exceptions to responses
src/Infrastructure/ Concrete implementations (DB migrator, repository impls)
```

Domain classes (`Form`, `FormField`, `FormSubmission`) are framework-agnostic aggregates with repository interfaces. Application services (`CreateFormService`, `SubmitFormService`) hold the only business logic. Controllers stay thin.

---

## 4. REST Controller Convention

All controllers extend `src/API/RestController.php`.

- Route registration via `src/API/ApiServiceProvider.php` → `rest_api_init`
- Namespace: `/all-feedback/v1/`
- Standard verbs: index, show, store, update, destroy
- Response helpers: `successResponse()`, `errorResponse()` — envelope is `{ success: bool, data: mixed }`
- Permission helpers: `publicPermission()`, `adminPermission()`, `authenticatedPermission()`
- Argument schema builders on the base class avoid repeated WP schema arrays

---

## 5. Database Migrations

- Files in `database/migrations/` named `NNNN_ClassName.php`
- `src/Infrastructure/Database/Migrator.php` discovers, versions, and runs them
- Ran migrations tracked in `wp_options` under `_allfb_migrations`
- Executed automatically on `admin_init` if any are pending
- Each migration implements `up()` / `down()` for reversibility
- Hooks fired before/after each migration for extensibility

---

## 6. Hooks Trait

`src/Traits/Hooks.php` wraps `add_action()`, `remove_action()`, `do_action()`, etc.

Any class that needs to register WordPress hooks uses this trait instead of calling globals directly. Makes dependencies explicit and simplifies future unit testing.

---

## 7. Singleton Trait

`src/Traits/Singleton.php` enforces a single instance via private constructor + static `getInstance()`.

Used by `Plugin` and `Modules/ModuleRegistry`. Guards against double-boot during WordPress page lifecycle.

---

## 8. React Query (TanStack Query) Pattern

- A single `queryClient` is created in `resources/scripts/admin/index.tsx` and shared app-wide.
- Query definitions live in `resources/scripts/admin/queries/` — each file exports typed query/mutation options.
- Query keys follow a nested array structure (`['forms', id]`) to allow precise cache invalidation.
- Mutations call the query client's `invalidateQueries` on success.
- Devtools (`ReactQueryDevtools`) are rendered only in dev builds.

---

## 9. TanStack Router (Hash SPA)

- Hash history is used so WordPress admin can load the SPA without server-side routing.
- Routes are file-based under `resources/scripts/admin/routes/`.
- `routeTree.gen.ts` is auto-generated by the TanStack Router webpack plugin — do not edit manually.
- Layout routes (`__root.tsx`, `_app.tsx`) provide shell and shared data loaders.
- Route loaders pre-fetch data before the component mounts (avoids loading spinners on nav).

---

## 10. API Client Pattern (Frontend)

- `resources/scripts/admin/api/` contains resource modules (one per domain entity).
- Each module exports typed functions that call `@wordpress/api-fetch` with the correct path and nonce.
- `@wordpress/api-fetch` middleware handles WP nonce injection automatically.
- No raw `fetch` calls in components — always go through the API module.

---

## 11. Module / Extension System

- `src/Modules/ModuleLoader.php` discovers and registers add-on modules.
- `src/Modules/ModuleRegistry.php` (singleton) holds registered modules.
- Each module can add REST routes, admin menus, and WP hooks without modifying core files.
- Allows third-party extensions with a stable integration surface.

---

## 12. Configuration Pattern

- `config/app.php` — returns an array of plugin identity, paths, URLs, and cache settings.
- `src/Support/Config.php` — thin wrapper injected where config values are needed.
- Prefer injecting `Config` over reading constants or `plugin_dir_path()` directly.

---

## 13. Survey Manager Pattern (table gateway)

`src/Survey/Manager.php` is the table gateway for `wp_af_surveys`. It differs from the DDD repository pattern used for the Form domain:

- No domain aggregate — returns `object` (stdClass) rows directly from `$wpdb->get_row()` / `get_results()`.
- JSON columns (`form_schema`, `settings`, `targeting`) are stored as raw strings and decoded by the controller in `prepareSurvey()`.
- All SQL lives inside Manager; controllers never call `$wpdb` directly.
- `insert()` stamps `created_at`; `update()` stamps `updated_at` automatically.
- `delete($id, false)` = soft-archive (status → archived). `delete($id, true)` = hard delete.
- `duplicate()` copies the row, prepends "Copy of" to title, resets status to draft and response_count to 0.
- Orderby columns are whitelisted against `ALLOWED_ORDERBY` before interpolation into SQL.
- When adding new CRUD operations follow the same phpcs-ignore pattern used in existing methods.

**Do NOT** mix this pattern with the DDD pattern. The Form domain uses `Domain/Form/FormRepository` interface + Application services. The Survey domain uses `Survey/Manager` directly from controllers.

---

## 14. Field Type & Status Constants

Centralised in `src/Survey/Manager.php` as public constants so controllers, validators, and future frontend config generation all derive from the same source of truth:

- `Manager::FIELD_TYPES` — allowed values for `field.type` inside `form_schema`
- `Manager::STATUSES` — allowed values for the `status` column: `draft`, `published`, `archived`

**Field type names must exactly match what the React builder emits.** Current list:

```php
// Metric types
'nps', 'csat', 'ces',
// Text input
'short_text', 'long_text',
// Choice
'radio', 'checkboxes', 'dropdown',
// Scale / rating
'star_rating', 'scale',
// Misc
'email', 'yes_no',
```

When adding a new field type: add it to `Manager::FIELD_TYPES` only — `SurveysController::validateFormSchema()` reads from that constant automatically. No other PHP file needs updating.

> **Naming rule:** Use the React builder's `FieldType` value as the canonical name. Do not use legacy WordPress/PHP naming conventions (`text`, `textarea`, `checkbox`) — those caused a breaking mismatch that was fixed in session 3.
